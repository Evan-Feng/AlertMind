# ADR-010: 阶段 4 LLM 分析引擎架构决策

## 背景

阶段 4 交付 LLM 分析引擎：`llm/base.py` 抽象、4 个 Provider（OpenAI / Claude / Qwen / Ollama）、
中文 Prompt、`core/analyzer.py`、`POST /api/v1/incidents/{id}/analyze`（PRD §8.4）。

相关 PRD 章节：
- §3.2 Incident 表字段（含 LLM 分析结果 6 字段）
- §4 API 契约（POST /incidents/{id}/analyze）
- §5 Provider 抽象（`AnalysisResult` + `LLMProvider` ABC）
- §6 核心中文 Prompt 模板
- §10 测试策略（LLM 调用在测试中 mock）
- §11 不要做的事（BackgroundTasks 够用，不引入 Celery）

本 ADR 在 W1 启动前锁定 11 个架构决策（A-K），阶段 4 所有 Wave 必须遵循；
Subagent 派发时引用本文档对应决策号，避免上下文重复 brief。

## Decision A：Provider 错误类型层次

### 裁决

`llm/base.py` 定义 1 个基类 + 5 个子类：

```
LLMProviderError (Exception)
├── LLMRateLimitError        # 429 / throttle
├── LLMAuthError             # 401 / invalid key
├── LLMTimeoutError          # network / read timeout
├── LLMProviderUnavailable   # 5xx / connection refused / model not loaded
└── LLMResponseFormatError   # JSON parse / Pydantic schema mismatch
```

每个 Provider 的适配层捕获原生异常（`openai.RateLimitError`、`anthropic.APIConnectionError`、
`httpx.ReadTimeout`）统一映射到上述子类；原生异常不外泄。

### 理由

切分依据是**调用方是否应该重试**：
- 前 4 个可重试（网络/服务临时问题）
- `LLMAuthError` 不重试（必须人工介入配置）
- `LLMResponseFormatError` 有限重试（prompt nudge 后模型可能改正）

### 替代方案

- **粗粒度（仅 LLMProviderError）**：调用方无法做重试决策，被动吞掉错误
- **细粒度（≥10 子类）**：维护成本高、覆盖长尾罕见场景收益低

### 未来可能调整

provider 原生异常若出现无法归入上述 5 类的情况（如 Ollama 模型未加载的 404），
默认包成 `LLMProviderUnavailable` + 打 warn 日志；需要新子类时单独提 ADR。

## Decision B：Structured Output 策略

### 裁决

**混合策略**：每个 Provider 用自己最可靠的原生 JSON 模式 + 统一 Pydantic 兜底校验。

| Provider | JSON 模式 |
|---|---|
| OpenAI | `response_format={"type": "json_object"}` |
| Claude | prefill assistant turn `{"`（anthropic SDK 原生支持） |
| Qwen | `response_format={"type": "json_object"}`（DashScope OpenAI 兼容端点） |
| Ollama | HTTP API `format: "json"` 参数 |

**统一兜底**：不管哪个 Provider，最终 LLM 返回文本都过 `AnalysisResult.model_validate_json(text)`；
校验失败抛 `LLMResponseFormatError`。

**硬约束（实测纪律）**：W4 每个 Provider 实现完成后，**必须本地手动跑 1 次真实 API**
验证 JSON 模式生效；避免"mock 测试都绿但真实 API 返回 markdown 代码块"的寂静失败。
实测脚本 W6 在 `scripts/debug_prompt.py` 中归档。

### 理由

- 纯 prompt 指令（"请返回 JSON"）对小模型的成功率只有约 50%，markdown 代码块包裹或字段缺失常见
- Provider 原生 JSON 模式成功率 > 95%
- Pydantic 校验抓剩下 5%
- 本地真实 API 实测防止 mock 假绿的寂静失败（真实 API 的 JSON 模式参数可能被 SDK 更新悄悄改动）

### 替代方案

- **仅靠 prompt 指令**：小模型不稳定
- **仅用 Claude tool_use（强 schema）**：代码复杂度显著上升且不能复用到其他 provider

### 未来可能调整

- Claude prefill 稳定率若 <90% 再切 tool_use（W6 实测后裁决，不在 W4 scope）
- OpenAI 的 `json_schema`（比 `json_object` 更强）成熟后可升级，但会绑定较新的 gpt-4 系列模型

## Decision C：Prompt 版本管理

### 裁决

**单文件 + 顶部常量**：

```python
# backend/alertmind/prompts/analyzer_zh.py
"""中文 Analyzer Prompt（阶段 4）。

PROMPT_VERSION 命名规范：{name}_{lang}_v{N}
- name: 用途（analyzer / summarizer / notifier）
- lang: 语言（zh / en）
- N: 递增版本号（不跳号）

本 prompt 的每次语义调整必须 +1 版本号，
并在 git commit message 的 body 明示改动点。
"""

PROMPT_VERSION = "analyzer_zh_v1"

ANALYZER_SYSTEM_PROMPT = "..."
ANALYZER_USER_PROMPT_TEMPLATE = "..."
```

`PROMPT_VERSION` 随每次 LLM 调用写入 `incident.prompt_version`（见 Decision F 字段清单），
支持未来 prompt A/B 对比、回归分析。

### 理由

- PRD §6 给的目标文件名是 `analyzer_zh.py`；命名已暗示语言可扩展，文件名格式稳定
- 目录结构 `prompts/analyzer/zh_v1.py` 在 v2 多语言/多变体 prompt 时再拆，当前过度设计
- 独立 `prompt_version` 字段不与 `llm_model` 合并的原因：字段职责单一，查询 / 过滤 SQL 简单

### 替代方案

- **prompt_version 写进 llm_model（如 `gpt-4o-mini/analyzer_zh_v1`）**：查询复杂、违反单一字段原则
- **单独目录 + 子文件**：YAGNI

### 未来可能调整

- v2 引入英文 prompt 时新建 `analyzer_en.py`，`PROMPT_VERSION = "analyzer_en_v1"` 独立计数
- 同一语言出现多 prompt 变体时（如 `analyzer_zh_with_runbook_v1` vs `analyzer_zh_v3`）考虑拆目录

## Decision D：重试 + 状态机 + API 响应

### 裁决

- **重试次数**：3 次，指数退避 1s / 2s / 4s
- **重试触发条件**：`LLMRateLimitError` / `LLMTimeoutError` / `LLMProviderUnavailable` 可重试；
  `LLMAuthError` 直接失败；`LLMResponseFormatError` 最多重试 1 次（nudge）
- **状态机**：`open → analyzing → open`；成功与失败都回落到 `open`；"是否已分析完成"由
  `analyzed_at IS NOT NULL` 判断，**与 `status` 字段解耦**
- **API 响应**：`POST /api/v1/incidents/{id}/analyze` 立即返回 **202 Accepted**，
  真实 LLM 调用走 FastAPI `BackgroundTasks`
- **失败不 re-raise**：仿 `safe_aggregate` 模式，写结构化日志 + status 回 `open`，不返回 5xx

### 理由

- LLM p99 延迟 10-30s，同步 API 会被上游（Alertmanager / nginx）判定为挂掉
- status / analyzed_at 解耦的原因：status 是"事件生命周期"（open/resolved），analyzed_at 是
  "衍生数据是否新鲜"；混在一个字段里会让 UI 逻辑混乱
- 202 + 后台执行符合 PRD §11"BackgroundTasks 够用"

### 替代方案

- **同步等待 + 500**：会拖慢 webhook 链路
- **用 Celery**：违反 PRD §11
- **status 上增加 `analyzed` 终态**：无谓增加 enum 值，且 `analyzed_at` 已经能表达

### 未来可能调整

- `analyzing` 状态卡死（进程崩溃导致不回退）的处理：**阶段 6 加"定时扫 analyzing > 10min 的
  incident 强制回 open"**，不在阶段 4 scope

## Decision E：Token 预算 + Prompt 截断

### 裁决

**首尾采样 5 + 10 + meta 独立** 策略：

```
默认参数（可环境变量覆盖）：
- ANALYZER_MAX_ALERT_SAMPLES_HEAD = 5    # 最早 5 条
- ANALYZER_MAX_ALERT_SAMPLES_TAIL = 10   # 最新 10 条
- 每条 alert 压缩后 ≤ 300 tokens

meta 信息单独塞进 prompt 的"告警数量" section：
- 总 alert_count
- 时间跨度（first_seen → last_seen）
- severity 分布（如 "5 critical, 2 warning"）
- unique alertname 列表（去重）
- 一句话："本次提供最早 5 条与最新 10 条样本（共 N 条）"

若 incident.alert_count ≤ 15，全量传，不做采样。
```

每条 alert 序列化时仅保留：alertname / severity / 过滤高熵 label 后的 labels / 
annotations.summary / starts_at。

### 理由

- **首尾采样**保留"事件演化轨迹"（起点信号 + 当前状态），均匀或随机采样会丢触发源头
- **5+10=15** 的量：对 gpt-4o-mini（128k context）无感；对 Ollama 小模型（4k-8k context）也能塞下
  （15 × 300 = 4500 token）
- 多给信息的边际收益 > 多花几分钱的边际成本（比 3+7 多 5 条 ≈ 多 500-1000 token，金额可忽略）
- **meta 独立**填补采样丢失的宏观视角

### 替代方案

- **3+7 采样**：信息量偏少，小模型 context 不是瓶颈
- **按 label 去重采样**：label 多样性本身是有用信号，过早聚合会让 LLM 看不到扩散范围
- **全量传**：alert_count > 50 时 token 成本线性上升，且对分析精度贡献边际递减

### 未来可能调整

- 阶段 5 Dashboard 有使用数据后重新评估采样数（如 HEAD=10/TAIL=20 是否显著提升分析质量）
- 若引入 Runbook RAG（v2），context section 会接入 RAG 结果，meta 格式需调整

## Decision F：Schema 3 字段分层 + TD-004 完整字段清单

### 裁决（3 字段分层）

| 字段 | 类型 | 语义 | 长度约束 | 示例 |
|---|---|---|---|---|
| `title` | String(512) not null | **Dashboard 卡片标题**（一句话概括事件） | ≤ 60 字 | "支付服务数据库连接池耗尽" |
| `summary` | Text null | **卡片副标题**（现象 + 规模，紧跟 title 之下） | ≤ 150 字 | "5 个 pod 连接池打满，下游超时率 40%" |
| `root_cause` | Text null | **详情页正文**（完整根因分析） | 无限 | 详细推断链条 + 证据 |

LLM prompt 必须同时产出 `title + summary + root_cause + impact + suggestions` 5 字段，
Pydantic schema 校验长度约束。

**summary 字段的精确语义**：Dashboard 列表卡片的副标题，补充 title 没说清的"现象 + 规模"上下文。

✅ **正例**：

- "5 个 pod 连接池打满，下游 API 超时率 40%"
- "3 节点 CPU 持续 >90% 达 20 分钟"

❌ **反例（禁止出现的内容）**：

- root_cause 的前 150 字节选 ← 违反分层职责（这是 root_cause 的事）
- 建议语（"立即扩容" / "重启 Pod"） ← 违反分层职责（这是 suggestions 的事）
- 和 title 重复的语句 ← 信息冗余
- "详见下方分析"之类的跳转提示 ← 副标题不是导航组件

**实现约束**：LLM prompt 必须对 title / summary / root_cause 分别下达不同要求，
并在 `AnalysisResult` 的 field_validator 里做长度限制（防止 LLM 把 root_cause 内容塞进 summary）。

### 裁决（alembic 0003 完整字段清单）

| 字段 | 类型 | Nullable | 来源 | 说明 |
|---|---|---|---|---|
| `title` | String(512) | NOT NULL | 已有（aggregator 写占位） | LLM 分析后覆盖 |
| `summary` | Text | NULL | 已有（W1 占位字段） | 本次锁定语义为"副标题 ≤ 150 字" |
| `root_cause` | Text | NULL | 新增 | LLM 根因分析 |
| `impact` | Text | NULL | 新增 | LLM 影响范围 |
| `suggestions` | Text | NULL | 新增 | LLM 处置建议（markdown 列表） |
| `llm_model` | String(128) | NULL | 新增 | 使用的模型名 |
| `llm_tokens_used` | Integer | NULL | 新增 | 本次分析 total token 数 |
| `analyzed_at` | DateTime(tz=True) | NULL | 新增 | 分析完成时间 |
| `prompt_version` | String(64) | NULL | 新增 | 见 Decision C |

**status CheckConstraint 扩展**：`status IN ('open', 'analyzing', 'resolved')`。
PostgreSQL 不支持直接 ALTER CHECK，migration 必须先 `DROP CONSTRAINT` 再 `ADD CONSTRAINT`。
migration 必须实现 downgrade 逻辑（回退到 open/resolved 二值）。

### 理由

- **title 保留 + LLM 覆盖**：aggregator 创建时 title 是占位，LLM 分析后覆盖更精准
- **summary 保留、语义锁死**：不是 title 缩短版，是副标题补充现象+规模，与 root_cause
  （完整分析）职责分离。未来 Dashboard 卡片可以两行显示 title + summary
- **prompt_version 独立字段**：A/B 对比 / 回归分析必须字段；阶段 4 多加 1 字段成本 = 阶段 7 补的 1/3

### 替代方案

- **summary 合并到 root_cause**：Dashboard 列表需要一行文字时必须再截断，不如专用字段
- **prompt_version 不要**：未来 prompt 变更后历史 incident 无法追溯当时用的是哪版
- **status 加 "analyzed" 终态**：与 `analyzed_at IS NOT NULL` 重复（见 Decision D）

### 未来可能调整

- 若实测证明 `title` 和 `summary` 用户认知上重复，阶段 7 考虑合并（有迁移成本但可控）
- 若引入 Runbook RAG 后分析结果需要"引用的 runbook id 列表"，新增字段 `related_runbooks jsonb`

## Decision G：SDK 选择

### 裁决

**不新增 SDK 依赖**：

| Provider | 实现方式 | 依赖 |
|---|---|---|
| OpenAI | openai SDK | 已锁 `openai>=1.55` |
| Claude | anthropic SDK | 已锁 `anthropic>=0.39` |
| Qwen | **复用 openai SDK**，只换 `base_url` | 零新增 |
| Ollama | **httpx 直接 HTTP 调用**（`/api/chat`） | 已锁 `httpx>=0.28` |

### 理由

- `dashscope` SDK 异步支持不完善、文档以阿里云控制台为主、迭代慢；DashScope OpenAI 兼容
  端点已经稳定
- `ollama-python` 异步 API 才成熟半年（0.3.x），AlertMind 只用 `/api/chat` 一个 endpoint，
  httpx 直接调更可控（超时、重试、cancel 都是 httpx 原生语义）
- 依赖越少，阶段 7 打磨 + 未来 pinning 冲突风险越低

### 替代方案

- **Qwen 用 dashscope SDK**：新增 1 个依赖 + 学习另一套异常体系，ROI 低
- **Ollama 用 ollama-python**：异步尚未稳定，且只用 1 个端点时直接 httpx 更简单

### 未来可能调整

- Qwen 若发现 OpenAI 兼容端点不支持关键特性（如 JSON mode 的 seed 参数），再切 dashscope SDK
  （新增依赖 scope 独立 commit）

## Decision H：测试策略

### 裁决

- **单元测试**：Mock provider 覆盖 **5 类场景**：
  1. `ok`：合法 JSON，所有字段合规
  2. `rate_limit`：抛 `LLMRateLimitError`，验证重试 3 次
  3. `parse_fail`：返回 markdown 代码块包裹 JSON，验证 Pydantic 兜底抛
     `LLMResponseFormatError` + 触发 1 次 nudge 重试
  4. `empty`：返回空 title，验证 schema 校验失败
  5. **`truncated`**：合法 JSON 但被 max_tokens 截断（某个字段无句末标点）
- **AnalysisResult Pydantic field_validator**：

```python
@field_validator("root_cause", "impact", "suggestions")
@classmethod
def must_end_with_terminator(cls, v: str) -> str:
    if v and not v.rstrip().endswith(("。", ".", "!", "?", "！", "？")):
        raise ValueError("response truncated")
    return v
```

- **集成测试**：走测试 `db_session`，完整链路 webhook → aggregator → analyzer（mock provider）→
  验证 incident 字段写回
- **真实 API 集成测试**：**不进 CI**（遵守 PRD §10）
- **手动 smoke**：`scripts/debug_prompt.py`，W6 本地跑 OpenAI / Ollama 各一次；该脚本也承担
  Decision B 的"每 provider 实现完跑 1 次真实 API"职责
- **VCR / 录制重放**：**不引入**（YAGNI）

### 理由

- PRD §10 明确"LLM 调用在测试中 mock"；今早才把 mypy 变成守门员，不能再引入真实 LLM 调用
  让 CI flaky
- `truncated` 场景在实际运行中较常见（max_tokens 命中）；句尾标点校验是最小成本的截断检测
- field_validator 让"检测截断"这件事落在 Pydantic 层，所有 provider 自动复用

### 替代方案

- **仅 4 类 mock**：`truncated` 漏网导致生产偶发存入断句不完整的 root_cause
- **VCR 录制真实 API 响应**：MVP 阶段 mock fixture 够用，增加依赖

### 未来可能调整

- 阶段 5 前若 Ollama 落地出现某类 mock 未覆盖的失败模式，补 `ollama_specific` 场景
- v2 引入 Runbook RAG 后 mock 矩阵扩展到 RAG miss / RAG noise 两类

## Decision I：自动触发策略

### 裁决

**仅 on-create + 手动触发**，**不实现翻倍策略**或任何自动刷新。

- 新建 incident：`aggregator.aggregate_one` 成功创建新 incident 后，立即
  `background_tasks.add_task(safe_analyze, incident_id)`
- 归并到已有 incident：**不触发**重新分析
- 手动 `POST /api/v1/incidents/{id}/analyze`：强制重新分析，无视 `analyzed_at` 新旧
  （作为 escape hatch）

**Hook 点选择**：在 `aggregate_one` 成功 return 前立即 schedule 任务，而非 batch 循环末尾统一 schedule。

```python
# aggregator.aggregate() 伪代码
for alert_id in alert_ids:
    result = aggregate_one(alert, db, embedder)
    if result.is_new_incident:
        background_tasks.add_task(safe_analyze, result.incident_id)  # ← Hook 点
    await db.flush()
```

理由：

- **故障隔离**：batch 中某条 alert 处理失败时，已成功创建的 incident 仍能被分析（不因一条
  坏苹果毁一筐）
- **事件驱动语义**：incident 创建 → 立即 schedule 分析，时间紧耦合符合直觉
- **BackgroundTasks 本身就是排队系统**，执行顺序不受 schedule 时机影响（reschedule 成本 ≈ 0）

### 理由

- **翻倍策略非线性刷新用户体验难预测**：1→2→4→8 条 alert 时分别重新分析，用户不知道
  下次看到的 root_cause 是什么时候生成的
- **on-create 已解决 80% 场景**：首次分析是最有价值的时刻（事件刚发生，分析最紧迫）
- **N→N+1 的边际分析价值低**：聚合进同一 incident 的 alert 本就相似（cosine sim > 0.85），
  新增 1 条对根因推断的信息增量有限
- **手动 /analyze 是 escape hatch**：用户觉得分析过期可以自己点
- **YAGNI**：阶段 5 有实际 Dashboard 使用数据后再决定是否加自动刷新，避免过早优化

### 替代方案

- **翻倍策略（1→2→4→8）**：被拒，理由见上
- **固定每 N 条触发**：同样非线性体验，且 N 值难选
- **每次归并都触发**：费用爆炸（单 incident 100 条 = 100 次 LLM 调用）

### 未来可能调整

阶段 5 Dashboard 有使用数据后可考虑：
- 引入"自动刷新开关"（Dashboard UI 控制，默认关闭）
- 基于用户明确反馈（"这个分析过期了"按钮）触发重分析

## Decision J：incident.title 的处理

### 裁决

- aggregator 创建 incident 时写占位 title（如 `"HighCPUUsage on node-1"`），**不加特殊后缀**
- LLM 分析成功后 **直接覆盖** title
- Dashboard 通过 `analyzed_at IS NOT NULL` 判断"是否已分析"，**不通过 title 格式**

### 理由

- title 被 LLM 覆盖更精准
- `analyzed_at` 判断分析状态比 title 格式检查稳定（未来 LLM title 格式可能变化）
- 占位 title 加后缀（如 "(待分析)"）会污染未启用 LLM 的部署形态

### 替代方案

- **LLM 输出存 summary，不覆盖 title**：title 质量差，Dashboard 卡片不好看
- **title 加"(待分析)"后缀**：污染 title 语义 + 下游代码要处理后缀

### 未来可能调整

若实测 LLM title 质量不稳定（超 60 字 / 乱码 / 英文），W5 联调时改为"保留原 title +
LLM title 写入 summary"

## Decision K：POST /analyze 的并发保护

### 裁决

**仅用 DB UPDATE WHERE 原子锁**，不引入 Redis 分布式锁。

```python
result = await db.execute(
    update(Incident)
    .where(Incident.id == incident_id)
    .where(Incident.status != "analyzing")
    .values(status="analyzing")
)
await db.commit()  # ⭐ 必须在 add_task 之前显式 commit

if result.rowcount == 0:
    existing = await db.get(Incident, incident_id)
    if not existing:
        raise HTTPException(status_code=404, detail="incident not found")
    return JSONResponse({"detail": "analysis in progress"}, status_code=409)

# 注意：此时 DB 已 commit，safe_analyze 在独立 session 中能看到 status='analyzing'
background_tasks.add_task(safe_analyze, incident_id)
return {"incident_id": incident_id, "status": "analyzing"}, 202
```

**Commit 边界要求**：UPDATE 执行后**必须显式 `await db.commit()`**，**在 `background_tasks.add_task()` 之前**。

**为什么必须显式 commit**：

- FastAPI BackgroundTasks 在 response 发送后执行
- `safe_analyze` 内部通过 `new_session()` 建新 DB session（参考 `safe_aggregate` 的镜像设计）
- 如果主 session 未 commit，新 session 看不到 `status='analyzing'` 的写入
- → 产生"重复分析"或"幽灵 analyzing 状态" bug

**通用规则**（跨决策）：凡是 "API handler 做 UPDATE + 后续 BackgroundTasks 读该 UPDATE" 的模式，
API handler 必须在 `add_task` 之前显式 commit。

### 理由

- DB `UPDATE ... WHERE status != 'analyzing'` 是天然原子锁，两个并发请求只有一个
  `rowcount == 1`
- 拒绝 Redis SETNX 避免新故障模式（Redis 瞬断 / TTL 到期但任务仍运行 / 锁丢失）
- 进程崩溃导致的 stuck incident 由"阶段 6 定时扫 analyzing > 10 min 回 open"解决
- **YAGNI**：当前只有单实例部署，多实例 + 分布式锁留到 v2

### 替代方案

- **Redis SETNX + DB 双保险**：增加复杂度和故障面，单实例场景收益为零
- **PostgreSQL advisory lock**：需要 transaction scope 管理，比 UPDATE WHERE 复杂
- **无任何锁**：两次并发 `/analyze` 会启两个 LLM 调用，费用 × 2 + 结果竞态覆盖

### 未来可能调整

- 多实例部署（v2 之后）需要分布式锁时重新评估：倾向 PostgreSQL advisory lock 而非 Redis
  （Redis 可作为 cache 层失败，advisory lock 与 transaction 生命周期强一致）
